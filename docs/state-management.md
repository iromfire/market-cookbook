# Управление состоянием <Badge type="warning" text="Не подтверждено командой" />

Состояние различается по **происхождению** и по **месту хранения**.

**Происхождение**

- **Server State** — данные бэкенда. Асинхронны, это снапшот на момент запроса, быстро устаревают.
- **Client State** — данные, которые рождаются в браузере.

**Место хранения** выбирается по требованиям к состоянию:

| Место         | Выбирай, если                                                                                    | Пример                                                             |
| ------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| **URL**       | состояние должно переживать перезагрузку и передаваться ссылкой, либо приходит извне через адрес | пагинация, активный таб, id сущности, токен в hash после редиректа |
| **Форма**     | нужен промежуточный ввод с валидацией до отправки                                                | редактирование договора до сохранения                              |
| **Компонент** | состояние нужно одному компоненту и его детям (через `input()`)                                  | открытый дропдаун, загруженный список на странице                  |
| **Store**     | состояние читают несколько компонентов, есть бизнес-логика, обновления                           | таб «Договор» в закупке                                            |

> Эффективный стейт-менеджмент — это выбор подходящего инструмента для каждого вида состояния. **В этой статье основной фокус сделан на сторе**, так как именно его организация наиболее сложна и менее тривиальна на практике.

## Когда использовать стор

✅ Создавай стор, когда состояние используется во многих компонентах, содержит сложную бизнес-логику и требует централизованного управления обновлением

::: tip ℹ️

Например, таб «Договор» в закупке

:::

❌ Не создавай стор без надобности

::: tip ℹ️

Например, если страница просто запрашивает данные с BE и отображает их, достаточно передать их в дочерние компоненты через `input()`, если это не приводит к props drilling

:::

## Виды сторов

| Вид               | Область действия                           | Пример                                                           |
| ----------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| **Global store**  | Состояние, доступное всему приложению      | Профиль пользователя, тема приложения, настройки тенанта         |
| **Feature store** | Состояние одной фичи или страницы          | Страница закупки                                                 |
| **Factory store** | Отдельное состояние для каждого экземпляра | Таб «Договор» в закупке, где каждый договор имеет своё состояние |

::: tip ℹ️

Выбирай минимально необходимую область: глобальный стор нужен только для данных, которые используются сквозь всё приложение

:::

## Выбор инструмента

✅ Используй `@ngrx/signals` [Документация](https://ngrx.io/guide/signals/signal-store)

❌ Не используй самописные решения (`BaseStore`, `BaseSignalStore`, сервис с `signal`/`Observable`)

## Структура стора

✅ Все данные фичи храни в одном сторе

❌ Не создавай сторы, которые хранят одно поле

## Источник истины

✅ Храни данные только в одном месте

❌ Не храни одни и те же данные в нескольких местах

::: tip ℹ️

Например, в сторе и в form-сервисе одновременно

:::

## Границы ответственности

✅ Храни в сторе только состояние, а не UI-детали

❌ Не клади в стор временные флаги UI (hover, opened, selected и т.д.)

## API стора

✅ Держи API стора простым и понятным

❌ Не раздувай стор десятками методов без необходимости

## Доступ к состоянию

**Правило:** компонент, которому нужны данные из стора, берёт их сам через `inject()`. Родитель не пробрасывает их через `input()`.

**Почему:** родитель не становится посредником, шаблон не знает о форме данных стора, а компонент можно использовать без привязки к конкретному месту в дереве.

✅ Стор инжектится там, где данные нужны

```ts
// ContractStatusComponent
private readonly _store = inject(ContractStore);

readonly status = this._store.status;
```

Родитель просто подключает компонент:

```html
<app-contract-status />
```

❌ Родитель читает стор и передаёт значение вниз:

```html
<app-contract-status [status]="store.status()" />
```

```ts
// ContractStatusComponent
readonly status = input<ContractStatus>();
```
